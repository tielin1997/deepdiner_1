# Prototype Report: Core Loop

## Hypothesis
"卡牌耐久度 + 吞噬转化"的组合能产生有意义的策略决策。玩家会在"保留卡牌还是现在打出"、"逼食客破产还是让他付钱"之间产生纠结。

## Approach
- 单文件 MonoBehaviour（~450 行），Unity UGUI 运行时构建 UI
- 硬编码 4 种食客、7 张按品质分级的初始手牌（普通/优秀/稀有/史诗）
- 实现完整回合流程：食客分配 → 选牌出牌 → 结算判定 → 吞噬生成新牌
- 跳过牌库/抽牌、商店、遗物、动画等非核心机制
- 耗时：1 个开发会话

## Result
- 核心循环可玩，玩家能够在"消耗耐久度打出加菜"和"保留卡牌"之间做出有意义的选择
- 品质分级（普通低价高耐久 vs 史诗低价低耐久）产生了明确的策略权衡
- 吞噬转化机制为"故意让食客破产"提供了强烈动机——获取更强卡牌
- Bill 变红的视觉反馈帮助玩家判断吞噬时机
- 耐久度归零销毁（Exhaust）产生了资源消耗的紧张感

## Metrics
- 食客类型：4 种（哥布林/史莱姆/深渊鱼/兽人）
- 卡牌品质：4 档（Common 10-19, Uncommon 20-29, Rare 30-39, Epic 40-50）
- 每日目标：150 起步，每日 +60
- 回合数：每天 4 轮，每轮 1-3 个食客

## Recommendation: PROCEED

核心机制验证通过。卡牌耐久度与吞噬转化的组合成功创造了策略决策空间。品质分级系统为卡牌使用提供了有意义的优先级排序。建议进入正式设计阶段，优先设计 MVP 5 个系统的 GDD。

## If Proceeding

### 架构要求
- 牌库/抽牌/弃牌堆系统需补充设计（原型中跳过）
- 卡牌状态机需规范化（耐久度衰减、Exhaust、Buff 修改）
- UI 需使用 TEngine UIWindow/UIWidget 模式重写

### 性能目标
- 原型无性能问题（纯 UI 交互）
- 生产版本需关注卡牌数量增长时的 UI 刷新效率

### 范围调整
- 食客金币和卡牌价格的数值已初步校准，后续通过 Luban 配置表精调
- 吞噬生成的卡牌数值需与初始卡牌做差异化平衡

### 预估生产工作量
- MVP 5 个系统 GDD 设计：5-8 个会话
- MVP 代码实现：按 systems-index 设计顺序推进

## Lessons Learned
1. **品质分级有效**：白绿蓝紫的颜色区分让卡牌价值一目了然，降低认知负担（支撑设计支柱1：高易用性）
2. **数值范围需注意**：卡牌加菜价格（10-50）与食客金币（30-180）的比例关系直接影响吞噬频率，需要精确调参
3. **吞噬动机强**：吞噬后获得更强卡牌的正反馈循环是核心驱动力，食谱进化系统应强化这一感受
4. **UI 即时反馈重要**：Bill 实时变红/变绿帮助玩家快速判断，生产版本应保留并加强
